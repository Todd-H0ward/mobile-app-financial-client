# План бюджета и «план vs факт»

Пункт 2.5.5 и одна из трёх самостоятельных механик, названных в критериях 8.3.
Самая важная часть ТЗ и два самых важных экрана проекта.

Суть: **ребёнок распределяет деньги до того, как начнёт их тратить**, а в конце
периода видит, где план разошёлся с реальностью. Магазин и копилка без этого
этапа — просто трата денег, а не планирование.

## Три направления

Минимум по ТЗ — три. Больше не вводим: три категории ребёнок начальной школы
удерживает в голове, пять — уже нет.

| Направление | Что это | Пример |
| --- | --- | --- |
| `needs` — обязательное | То, без чего период не закрыть | еда, отопление |
| `wants` — необязательное | То, что хочется | игрушка, украшение комнаты |
| `savings` — накопления | Отложенное на цель | на самокат |

Названия направлений на экране — детские и одинаковые везде: «Нужное»,
«Хочется», «Копилка». Ровно те же три слова звучат в онбординге (2.5.1), в
каталоге покупок (2.5.6) и в итогах, иначе связь не собирается.

## Экран планирования

```
Доступно в этом периоде: 120 монет

Нужное     ▓▓▓▓▓▓▓▓░░  60
Хочется    ▓▓▓░░░░░░░  25
Копилка    ▓▓▓▓░░░░░░  30

Осталось распределить: 5
                    [ Подтвердить план ]
```

Правила экрана:

1. **Остаток виден всегда** и пересчитывается на каждое движение ползунка.
2. **Превысить сумму нельзя** — ползунок упирается в остаток. Не предупреждение
   постфактум, а физический предел: ребёнок не должен узнавать об ошибке после
   подтверждения.
3. **Нераспределённый остаток допустим.** Требование — не превысить, а не
   раздать всё до монеты. Остаток переходит в следующий период и об этом
   сказано на экране.
4. **План подтверждается явно.** До подтверждения тратить нельзя — иначе этап
   планирования становится необязательным и превращается в экран-заставку.
5. **Ноль по направлению разрешён**, но подтверждение спросит: «На нужное не
   выделено ничего. Еду и тепло будет не на что купить. Всё равно?» —
   предупреждение с объяснением последствия, а не запрет.

## Контроль во время периода

Пока период активен, каждая трата уменьшает факт по своему направлению.

- Трата **сверх выделенного по направлению** не блокируется, но показывается:
  «Ты планировал 25 на „хочется“, эта покупка сделает 32». Ребёнок волен
  решить — это и есть решение, которому мы учим.
- Трата **сверх общего баланса** блокируется всегда, с объяснением, чего не
  хватает и какие есть варианты (2.5.6) — см.
  [economy.md](./economy.md#запрет-отрицательного-баланса).
- Разница между «превысил направление» и «превысил кошелёк» принципиальна:
  первое — урок, второе — правило.

## Экран итогов: план vs факт

Показывается в фазе `summary`, см. [game-period.md](./game-period.md).

```
Период 2 — итоги

              План   Факт
Нужное          60     58   ✓ уложился
Хочется         25     40   +15 больше плана
Копилка         30     15   −15 меньше плана

Что произошло: на «хочется» ушло на 15 больше, и эти 15
не попали в копилку. До самоката осталось 85 вместо 70.

Что можно сделать в следующем периоде:
· отложить в копилку сразу после начисления
· перенести одну покупку из «хочется» на потом
```

Три обязательных части:

1. **Сравнение** по каждому направлению — план, факт, знак расхождения.
2. **Объяснение причины**, связывающее расхождения между собой. Не «вы
   перерасходовали», а «эти 15 не попали в копилку» — ребёнок должен увидеть,
   что деньги не исчезли, а ушли в другое место.
3. **Путь восстановления** (2.5.9): один-два конкретных шага на следующий
   период. Без обнуления прогресса и без оценки.

Цветом расхождение не кодируется — знак и текст несут смысл сами, см.
[accessibility.md](./accessibility.md). Перерасход не красный: красный читается
как ошибка, а это не ошибка, а результат решения.

## Модель данных

```ts
/** Сколько ребёнок выделил по каждому направлению. Монеты, целые, ≥ 0. */
interface BudgetPlan {
  /** Обязательные расходы: еда, отопление. */
  needs: number;
  /** Необязательные: игрушки, украшения комнаты. */
  wants: number;
  /** Отложенное на финансовую цель. */
  savings: number;
}

/** Сколько реально ушло. Та же форма, чтобы сравнение было вычитанием. */
type BudgetFact = BudgetPlan;

/** Строка сравнения, одна на направление. */
interface BudgetComparison {
  /** Направление: 'needs' | 'wants' | 'savings'. */
  direction: BudgetDirection;
  /** Запланировано на период. */
  planned: number;
  /** Фактически потрачено или отложено. */
  actual: number;
  /** actual − planned. Отрицательное — потрачено меньше плана. */
  delta: number;
}
```

`BudgetFact` намеренно той же формы, что и `BudgetPlan`: сравнение сводится к
вычитанию, и ни один экран не пересобирает структуру заново.

## Формулы

```
доступно      = баланс кошелька на входе в планирование
остаток       = доступно − (plan.needs + plan.wants + plan.savings)
инвариант     = остаток ≥ 0            ← проверяется на каждое изменение
delta[i]      = fact[i] − plan[i]
уложился      = |delta[i]| ≤ TOLERANCE  ← TOLERANCE = 0, точное сравнение
```

`TOLERANCE` вынесен в таблицу баланса именованной константой на случай, если
на плейтесте «ровно в ноль» окажется недостижимо часто.

## Тесты

- сумма плана никогда не превышает доступное — свойство, а не проверка на экране;
- нулевое направление разрешено и даёт предупреждение, а не отказ;
- факт копится по направлениям и совпадает с историей кошелька до монеты;
- сравнение возвращает строку на каждое из трёх направлений даже при нулевом
  плане и нулевом факте — пустой экран итогов недопустим;
- нераспределённый остаток переходит в следующий период и не теряется.
